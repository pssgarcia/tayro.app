Plataforma de creators fitness, **creator-first**. MVP de plataforma de marketing de influência. Infra real = Neon (Postgres serverless).

## Cérebro do produto → `.claude/knowledge/`
Este arquivo é **como construir** (stack, convenções, footguns, o que já está pronto).
O **o quê e por quê** mora em `.claude/knowledge/` — versionado de propósito (ver `.gitignore`):

Não duplicar conteúdo entre os dois lugares. Fluxo de produto: `/feature` → `/research` → `/architect` → implementar (TDD) → `/review`.

## O que cada capacidade faz agora → `specs/`
Terceira categoria, além das duas acima: `specs/<slug>/spec.md` (raiz do repo, ver `specs/README.md`) descreve o comportamento **vivo** de cada capacidade de domínio (Application, Reward, Instagram sync, etc.) — **editar a spec é o pedido de mudança**, não documentação que se atualiza depois do fato. `/architect` cria e mantém esses arquivos (capacidade nova exige veredito `AGORA` do `/feature`; capacidade existente não — editar a spec é o próprio atalho). `/review` confere deriva: código que mudou comportamento sem atualizar a spec correspondente é achado de revisão. Diferença de `decisions.md`: decisão registra por que decidimos X uma vez e nunca se edita; spec registra o que X faz hoje e se edita sempre que o comportamento muda.

- **CD vermelho com deploy OK — era o Railway CLI, não o build (RESOLVIDO 2026-08-22 — `--detach` + poll, ver abaixo). NÃO usar `@latest` no workflow.** Histórico do problema, 3 encarnações do mesmo falso-negativo:
  - *Flake de log-streaming (2026-08-03, runs #38/#40):* `railway up --ci` saía com `Failed to stream build logs` ~65s após o início, deploy completando normal. Fix na época: retry de 1 tentativa extra (v0.27.0/#74).
  - *Trava sem retornar (2026-08-15 → 2026-08-21):* a partir da **5.41.2** o CLI completava o build, publicava a imagem e **nunca retornava** — só morria no `timeout`, com a produção já atualizada. Workflow puxava `@railway/cli@latest`; um release do Railway quebrou o CD sem nenhuma mudança nossa (5.41.1 = último verde em 14/08; 5.41.2 e 5.42.x = 5 falhas seguidas). Tentativa de fix: **versão pinada** (5.41.1) no `cd.yml`.
  - **A versão pinada NÃO resolveu (2026-08-22):** o mesmo travamento aconteceu com a 5.41.1 pinada, num release que não tocava `apps/api` — o Railway respondeu "no changes detected in watch paths, build will skip" e o CLI travou do mesmo jeito, sem log pra transmitir. Ou seja, a causa nunca foi a versão do CLI — é o `--ci` (stream build logs, then exit) não detectar corretamente o fim do streaming, com ou sem build de verdade acontecendo.
  - **Fix real:** `up --detach` (sobe e retorna na hora, sem streaming) + poll pontual do status via `railway deployment list --json` até `SUCCESS`/`SKIPPED` (sucesso) ou `FAILED`/`CRASHED`/`REMOVED`/`REMOVING` (falha), com teto de 15min. Sem streaming longo, não tem como pendurar — e o job ainda falha de verdade se o build falhar (o que o `--ci` também garantia). Retry de 2 tentativas removido: não cobria nenhum dos dois modos de falha acima e só garantia +5min em toda falha real.
  - **Assinatura do problema antigo, pra reconhecer se voltar:** job durando ~10m30s cravado (300s + 300s + overhead) com as duas tentativas batendo no `timeout`. A migration roda no step ANTERIOR ao deploy — uma falha real dela ficava mascarada por esse vermelho crônico.
  - **4ª encarnação, diferente das 3 acima (2026-09-03, release v0.63.0/#197): desta vez o vermelho era de verdade.** O próprio `railway up --detach` travou 5min sem retornar (exit 124 no `timeout 300` que embrulha o `up`, não no poll que vem depois) — nem chegou a existir um deployment pra consultar status. A migration (`partnership_result_visibility`, que fazia `DROP COLUMN visibleToCreator`) já tinha rodado e commitado em produção no step anterior. Janela real, não cosmética: o código ANTIGO (ainda no ar, Prisma Client gerado contra o schema velho) tem `include: { result: true }` em `getPublicProfile` (`GET /creators/:handle/public`) — isso gera SQL que referencia `visibleToCreator`, e a coluna já não existia mais. `/c/:handle` quebrava com 500 pra qualquer creator com candidatura aprovada até o deploy ser refeito. Fechado reenviando só o job que falhou (`gh api .../rerun-failed-jobs`, sem re-rodar o Vercel que já tinha ido) — completou em 13m40s na 2ª tentativa. Ver a regra nova em "Convenções de trabalho" sobre migration destrutiva: o problema não foi a ORDEM migration→deploy (essa ordem é a certa pra migration aditiva), foi rodar um `DROP COLUMN` no mesmo release em que o código para de usar a coluna.

## CI/CD
- **CI** (`.github/workflows/ci.yml`): roda em todo PR — lint · typecheck · test · build (API e Web).
- **CD** (`.github/workflows/cd.yml`): no merge em `main`, após CI passar → migrations + deploy.
  - **O step de deploy tem teste: `bash .github/workflows/test/deploy-step.test.sh`.** Extrai o bloco `run:` do próprio `cd.yml` (não uma cópia, que envelheceria) e roda contra um `npx` falso, cobrindo os cenários que morderam de verdade: build concluído, build pulado por watch path, `FAILED`/`CRASHED`, upload falhando, id ausente na saída, JSON com wrapper diferente e status desconhecido. **Rodar antes de mexer nesse step** — ele só era exercitável mergeando na `main` e torcendo, e isso custou 6 releases vermelhas até a causa aparecer.
- **Git Flow:** `feature/* → develop → main`, sempre via PR. Branches protegidas (CI obrigatório + 1 aprovação, sem push direto/force-push) desde 2026-08-16 — **antes disso a proteção nunca tinha sido de fato aplicada no GitHub** apesar desta linha já afirmar isso; achado ao dar acesso Write a um colaborador externo (repo pessoal não suporta colaborador read-only, só Write). Config real fica no GitHub (Settings → Branches), não neste arquivo — conferir com `gh api repos/pssgarcia/tayro.app/branches/<branch>/protection` antes de assumir que está ativa.
- **SEMPRE partir da `develop` atualizada — regra nº 1, antes de qualquer código (MORDEU 2026-08-13).** `develop` tem que estar idêntica à produção antes de começar qualquer coisa. O primeiro comando de toda sessão de implementação é `git fetch origin`; depois conferir `git diff origin/develop origin/main --stat` (tem que vir **vazio** — os merge commits de release ficam só na `main`, então `git log` mostrar a develop "atrás" é normal, o que importa é o diff de conteúdo) e só então criar a branch a partir de `origin/develop`.
  - **Nunca confiar no CLAUDE.md, no snapshot de git status do início da sessão, nem em memória de sessão anterior** para saber a versão atual ou o que já foi entregue. Antes de afirmar que algo "não existe" / "não tem tela", verificar contra `origin/develop`, não contra a working tree.
  - O que custou ignorar isso: a `feature/campaign-lifecycle` saiu de uma base velha, a `main` já estava na v0.36.0 (não v0.30.0, como o CLAUDE.md local dizia), e o PR #104 saiu conflitado reimplementando "encerrar e apagar campanha" — que o #102 tinha entregue em produção 2 dias antes. Uma auditoria inteira do produto foi feita em cima de um retrato obsoleto e reportou como furo em produção coisas já corrigidas.

## Observabilidade (Sentry) — `D-20`
- **Inerte sem DSN.** `apps/api/src/instrument.ts` e `apps/web/src/instrument.ts` são o 1º import de `main.ts`/`main.tsx`. Sem `SENTRY_DSN`/`VITE_SENTRY_DSN` o `Sentry.init` não roda. **Em produção a API não sobe sem `SENTRY_DSN`** (`resolveSentryConfig` lança, mesma regra do `resolveAllowedOrigins`).
- **API:** `SentryGlobalFilter` (`APP_FILTER`, antes do `APP_GUARD` em `app.module.ts`) reporta o que **não** for `HttpException` e delega pro handler padrão do Nest — cliente segue com 500 genérico sem stack; 4xx mapeado nos services é fluxo de controle, **não vira evento, não há double-report**. A regra inviolável "stack trace nunca vaza pro cliente" continua valendo. Falha em background do `instagram-sync` (`scheduleRefresh`, roda depois da resposta HTTP) tem `Sentry.captureException` explícito no `.catch` — era invisível.
- **Web:** `Sentry.ErrorBoundary` no topo do `App` com `SentryFallback` (erro de render dava tela branca). `<Routes>` embrulhado por `withSentryReactRouterV7Routing` pra traces por rota.
- **Escopo:** erro não tratado + tracing amostrado a **10%** (`(VITE_)SENTRY_TRACES_SAMPLE_RATE`, default 0.1). **Session Replay DESLIGADO** — sem consentimento hoje, gravaria DOM de `/apply/:id` e `/auth/*` (LGPD). Não religar sem política de privacidade.
- **PII:** `sendDefaultPii: false` (sem IP) + `beforeSend` remove corpo de `/auth/*` e headers de auth nos dois apps. Sentry é **sub-processador** de dado pessoal (ver `roadmap.md` → LGPD Bloco 3).
- **Onde ficam os secrets:** Railway service env (`SENTRY_DSN`, `SENTRY_ENVIRONMENT`) pra API; Vercel project env (`VITE_SENTRY_DSN`, `VITE_SENTRY_ENVIRONMENT` + `SENTRY_AUTH_TOKEN`/`SENTRY_ORG`/`SENTRY_PROJECT` só pro upload de sourcemap) pra web. **Nada em GitHub Secrets.** Região **EU** (DSN tem `ingest.de.sentry.io`).
- **Release:** git SHA automático — `RAILWAY_GIT_COMMIT_SHA` (API), `VERCEL_GIT_COMMIT_SHA` via `vite.config.ts` → `process.env.VITE_SENTRY_RELEASE` (web).
- **Sourcemaps:** web = `build.sourcemap: 'hidden'` + `@sentry/vite-plugin` (inerte sem `SENTRY_AUTH_TOKEN`) com `filesToDeleteAfterUpload` — **nenhum `.map` servido nem no precache do PWA**. API = `node --enable-source-maps` + os `.js.map` do tsc, **sem** upload. `cd.yml` não muda (upload roda no build remoto da Vercel).
- **Como testar em prod:** rota/botão de erro temporário → conferir evento no Sentry com stack legível + tags `environment`/`release` certas → remover o gatilho.

## Regras de segurança (invioláveis)
- Secrets SEMPRE em `.env` / GitHub Secrets. Nunca no bundle, logs ou erros HTTP. **Nem em arquivo de teste/fixture** (MORDEU 2026-08-24: chave real da RapidAPI ficou commitada num `.spec.ts` desde a origem do arquivo — precisou rotacionar, apagar do arquivo não desfaz o vazamento no histórico do git).
- Guards em TODA rota autenticada. Endpoint público deve ser explícito e documentado.
- `@MaxLength()` em todo campo de texto livre (DTOs) — defesa contra payload spam/DoS.
- Refresh token invalidado no uso (rotation). Token roubado não pode mint forever.
- CORS com allow-list explícita.
- Throttle específico em `/auth/*` (5 req / 15 min por IP).
- Erros de infra (Prisma, HTTP externo) nunca vazam stack trace pro cliente.

## Decisões de domínio — não quebrar
- offer* em Campaign (offerAmount[centavos], offerType CASH|PRODUCT, offerDeadlineDays, offerDescription) = fonte de verdade da oferta. rewardType/rewardValue DEPRECATED — não escrever, não expor.

- Instagram: interface InstagramProvider + DI token INSTAGRAM_PROVIDER. Stub determinístico = default dev; RapidApi via env (mapeamento isolado, sem hardcode). Staleness 24h. Cooldown refresh-ig 15min carimbado em TODA tentativa (inclusive falha — senão FAILED é spammável e queima cota). Falha preserva último valor. calcEngagementRate = média de (likes+comments) POR POST / followers × 100, arredondada a 1 casa (função pura testada) — não é a soma das interações, somar inflaria a taxa. `igProfilePicUrl` = `hd_profile_pic_url_info.url ?? profile_pic_url ?? null` (v0.21.0).
- **Footgun CORP (JÁ NOS MORDEU, não repetir):** Instagram serve fotos de PERFIL (path `t51.82787-19`) com `Cross-Origin-Resource-Policy: same-origin` — browser bloqueia num `<img>` cross-origin, mesmo com URL válida e pública. Não é contornável no frontend (nem `referrerPolicy` nem `crossorigin` resolvem). Se algum dia a foto de perfil sumir de novo, ANTES de suspeitar do dado, inspecionar os response headers da URL da CDN.

## Auth no frontend — footguns (JÁ NOS MORDEU, não repetir)
- accessToken em Zustand (memória), NUNCA localStorage/sessionStorage. Refresh em cookie httpOnly.
- Silent refresh no boot do AppShell; guards avaliam SÓ depois do refresh resolver (senão race → /login).
- Interceptor de 401 NÃO usa window.location (loop de reload). Usa navigate do router, máx 1 redirect.
- /auth/refresh e /auth/login ISENTOS do retry de refresh do interceptor (senão loop infinito — foi o bug do login travado).
- **Qualquer endpoint que valide senha atual (401 = erro de negócio, não token expirado) TEM que viver em `/auth/*` (MORDEU 2026-09-04).** O interceptor de 401 (`services/api.ts`) trata todo 401 fora de `/auth/*` como sessão expirada e chama `clearAuth()` — regra que só é segura enquanto nenhum endpoint fora de `/auth/*` devolver 401 por motivo de negócio. `DELETE /influencers/me` (exclusão de conta) violou isso na 1ª versão: senha errada deslogava a creator em vez de mostrar "Senha incorreta", porque o interceptor limpava a sessão antes do componente conseguir renderizar o erro. Corrigido movendo pra `POST /auth/delete-account` (mesma casa de `changePassword`/`changeEmail`, que já respeitavam essa regra sem documentá-la explicitamente aqui). Teste de regressão real: `apps/web/src/services/api.spec.ts` exercita o interceptor de verdade (adapter axios sintético), não um mock de `api.post`/`api.delete` — um teste que mocka o client HTTP nunca passa pelo interceptor, e por isso não teria pego este bug.
- Poll-while-PENDING (teto ~45s) pra dados de IG assíncronos.

## Convenções de trabalho (somar às de performance)
- **Mudar comportamento de uma capacidade que já tem spec começa editando `specs/<slug>/spec.md`** (ou pedindo pro `/architect` desenhar a mudança nela), não direto no código. Ver `specs/README.md`.
- **`git fetch origin` + branch da `develop` atualizada ANTES de escrever qualquer linha.** Ver a regra completa em CI/CD — é o passo zero, não uma checagem opcional.
- Ler controllers/DTOs REAIS antes de assumir shape. Nunca inventar contrato.
- Um chunk por vez: PASSO 0 (contratos/gap) → OK → implementar.
- Rotas: literais antes de :id; públicas fora de guards.
- **Copy visível sai do DICIONÁRIO (`apps/web/src/i18n/`), nunca escrita direto no JSX (desde 2026-09-08).** O produto é bilíngue pt/en; string solta no componente não chega no `en.ts` e some da versão em inglês. Travado por `apps/web/copy-no-dicionario.test.ts`. Ver `i18n/README.md` pro que fica fora (erros da API, e-mails) e pra regra própria dos documentos legais, que são traduzidos mas vivem FORA do dicionário.
- **Rota, arquivo, hook, variável e endpoint em INGLÊS. Copy visível em PORTUGUÊS. (MORDEU 2026-09-04,
  e não foi a 1ª vez.)** Todas as rotas do produto são inglês: `/login`, `/register/brand`,
  `/apply/:id`, `/programs`, `/c/:handle`, `/forgot-password`, `/reset-password`, `/claim`,
  `/privacy-policy`, `/terms-of-use`. É a mesma decisão que manteve `/programs`, `ProgramCard`,
  `useProgram` e `POST /programs/:id/apply/public` em inglês quando TODA a copy passou de
  "Programa" para "Campanha" (2026-08-30). Uma rota em português entrou como `/termos-de-uso` e o
  Pedro pegou na revisão. **O caminho de um documento mora numa constante única**
  (`apps/web/src/config/legal.ts`) e a `<Route>` lê dela: definir o endereço no router E no
  componente que linka é exatamente como uma das duas sai em outro idioma.
- Labels/textos derivados do estado de domínio (ex: "pagamento" vs "envio" por offerType), não hardcoded.
- **Copy nunca assume o gênero de quem FAZ a ação (creator/marca) — reescrever pra falar do objeto (candidatura, campanha, conteúdo) ou usar 2ª pessoa.** Mordeu 3x em produção com o mesmo padrão (v0.24.0, 2026-08-23, 2026-09-02 na aba Creators): "Oferta à creator" → "Oferta do programa", "as creators aprovadas" → "as candidaturas aprovadas", "Aprovada em N campanhas" → "N candidaturas aprovadas". "Candidatura aprovada" pode ficar — ali o feminino é da palavra, não de quem se candidatou.
- **Verificação visual de UI: não confiar em screenshot de viewport estreito (volta em metade da resolução, texto pequeno some) nem em suíte de teste (não abre navegador de verdade).** Método que funcionou nas duas conferências que acharam bug real (Kinetic 2026-08-28, i18n 2026-09-09): medir overflow por DOM (`scrollWidth` vs `clientWidth` + varredura de elemento além do viewport + texto cortado), com a URL conferida no mesmo retorno, usando Playwright instalado FORA do repositório (scratchpad da sessão — nada entra no `package.json` nem no CI). Achados de proporção/peso visual continuam precisando de olho humano; a ferramenta pega overflow e erro de página, não "isso está feio".
- **Testar comportamento, não render:** mockar hooks só valida UI. Cobrir o happy path real + os gates de negócio. Antes de construir UI sobre endpoint "que já existe", LER a validação dele (mordeu em Recompensas: create exigia conteúdo aprovado, falhou silencioso em prod).
- **Manter este CLAUDE.md atualizado:** ao concluir feature/release, atualizar Feito / Pendente / Telas prontas.
- **Migration destrutiva (`DROP COLUMN`, `RENAME COLUMN`, mudança de tipo, `NOT NULL` sem default seguro) NUNCA no mesmo release em que o código para de usar o campo antigo (MORDEU 2026-09-03, ver CI/CD).** O CD roda migration→deploy em lockstep (correto pra migration aditiva: se a migration falhar, o deploy nem acontece). Mas numa migration destrutiva não existe ordem segura — se o deploy do código atrasar ou falhar DEPOIS da migration já ter rodado, o código antigo (ainda no ar) fica servindo contra um schema que não tem mais a coluna que ele espera; inverter a ordem só troca pelo problema oposto (código novo contra schema velho). A saída é sempre 2 releases (expand/contract): (1) migration só ADITIVA (coluna nova) + código já para de ler/escrever o campo velho, sem apagar a coluna ainda; (2) confirmado (1) estável em produção, release separada só com o `DROP COLUMN`, sem mudança de código junto. Cada release fica compatível com os dois schemas em qualquer ordem — não sobra janela pra quebrar.
